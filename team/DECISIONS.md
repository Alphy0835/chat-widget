## D-001: Два слоя документации — team/ (процесс) и docs/ (знания о продукте) (2026-07-06)
Решение: в шаблон добавляется папка `docs/` — урезанное ядро из внешнего docs-шаблона (`G:\Мой диск\docs шаблон`). `team/` описывает процесс (задачи, статусы, приёмка, решения), `docs/` — сам продукт (требования, архитектура, фичи, качество, безопасность, эксплуатация). При любом конфликте источник правды — `team/` и скилы ролей.
Почему: полный docs-шаблон (91 файл, 14 доменов) рассчитан на продуктовую компанию и дублирует механизмы команды. Дубли-источники правды исключаются из переноса: acceptance-criteria / definition-of-done → приёмка в PROTOCOL.md и критерии в задачах; bug-report-template → формат BUG-N в скиле /qa; architecture-decisions/ → team/DECISIONS.md; design-guide/ → team/design/; security-checklist → чеклист в скиле /security; sync-checklist → поле «Update together with» в паспорте каждого файла.

## D-002: Паспорт docs-файла — 4 поля (2026-07-06)
Решение: паспорт в шапке каждого файла `docs/` сокращается с 9 полей до 4: `Status`, `Source of truth`, `Update together with`, `Update trigger`.
Почему: Owner и Review required рассчитаны на команду людей; Doc ID дублирует путь файла; Related docs дублирует Update together with; Maturity уже описан централизованно в maturity-levels.md. Каждое лишнее поле — токены при каждом чтении любым агентом.

## D-003: Полная миграция docs-шаблона, архив в docs-archive/ (2026-07-06)
Решение: внешняя папка `G:\Мой диск\docs шаблон` удаляется пользователем, поэтому все 53 файла, не вошедшие в активный слой `docs/`, переносятся в `docs-archive/` в корне проекта с сохранением структуры. Архив — хранилище заготовок, а не рабочая документация: в паспортах те же 4 поля (D-002) и исправленные опечатки, но ссылки внутри архивных файлов не чинятся — их адаптируют при активации файла. В архиве два класса файлов (помечены в `docs-archive/README.md`): «отложенные» — тим лид переносит их в `docs/` при достижении maturity-уровня; «заменённые» (acceptance-criteria, definition-of-done, bug-report-template, security-checklist, sync-checklist, architecture-decisions/, design-guide/) — не активируются никогда, источник правды для них — `team/` и скилы (D-001), лежат только как справочный материал.
Почему: архив вне `docs/`, чтобы активный слой оставался чистым и grep-проверки приёмки по `docs/` (из TASK-001) не ловили архивные файлы. Альтернатива «не переносить заменённые» отвергнута: пользователь удаляет исходник и хочет сохранить всё.

## D-004: Технология и способ встраивания виджета (2026-08-11)
Решение: Виджет реализуется как frontend-модуль на чистом JavaScript (без фреймворков) + CSS, встраивается на сайт-клиент через один `<script>`-тег (loader), который создаёт контейнер и монтирует содержимое виджета внутри Shadow DOM. Backend для будущей связи ИИ-агента, менеджера и Битрикс24 будет на Python — реализуется отдельной задачей позже, вне текущего этапа.
Почему: требование пользователя — вставить ~10–15 строк в код сайта, и виджет должен отрисоваться, при этом код виджета работает отдельно от сайта. Это возможно только через JS, исполняемый в браузере — Python не подходит для клиентской отрисовки в браузере. Shadow DOM выбран вместо iframe: даёт изоляцию стилей без лишнего HTTP-запроса на отдельную HTML-страницу и не усложняет будущий обмен данными между виджетом и страницей (понадобится для передачи контекста ИИ-агенту). React/Vue отклонены — лишний вес для простого встраиваемого виджета, который должен быстро грузиться на чужих сайтах.

## D-005: Визуальный MVP-паттерн виджета без брендбука (2026-08-11)
Решение: Виджет реализуется по стандартному паттерну chat-виджета (как Intercom/Tawk.to): плавающая круглая кнопка (~60×60px) в правом нижнем углу экрана, по клику разворачивается в панель чата (~360×520px, на мобильных <480px — почти на весь экран). Стартовая цветовая схема нейтральная (primary `#2563EB`, фон окна белый, скругления 16px), без готового брендбука. На этом этапе внутри окна — только UI-оболочка: шапка (название/иконка-заглушка, кнопка закрытия), область сообщений с текстом-заглушкой, неактивное поле ввода и disabled-кнопка отправки. Позиция и основной цвет настраиваются через `data-*` атрибуты loader-скрипта.
Почему: пользователь подтвердил стандартный паттерн вместо кастомного дизайна — экономит время и бюджет, паттерн уже знаком пользователям сайтов. Настройка через конфиг заложена заранее, так как виджет заведомо будет ставиться на разные сайты с разным брендингом.

## D-006: Целевой сайт интеграции и фирменный стиль (2026-08-11)
Решение: Первый (пока единственный известный) сайт для интеграции виджета — https://pravoe-delo.su/ (юридическая компания «Правое дело», списание долгов/банкротство физлиц). Технически сайт собран на Tilda (`static.tildacdn.com`), собственного чат-виджета на момент проверки на сайте нет — конфликтов с уже установленными сторонними чатами не ожидается. Зафиксированный фирменный стиль сайта для дизайна виджета: акцентный цвет `#FF4800` (оранжевый, используется во всех CTA-кнопках), шрифт `"Roboto Condensed", Arial, sans-serif` (везде на сайте: вес 700 в заголовках, 400 в тексте), скругление кнопок ~10px, светлый/белый фон, чёрный текст.
Почему: без конкретного сайта-цели дизайн виджета выбирался бы вслепую; данные сняты напрямую с боевого сайта (computed styles), а не придуманы. Факт «Tilda + чистый HTML, без готового чат-виджета» дополнительно подтверждает, что способ встраивания из D-004 (script + Shadow DOM) применим без конфликтов на реальной площадке.

## D-007: Новый дефолтный акцентный цвет и шрифт виджета (2026-08-11)
Решение: Дефолтная тема виджета (значение `--cw-primary` при отсутствии `data-primary-color` у сайта-клиента) меняется с нейтрального синего `#2563EB` (D-005) на `#FF4800` — цвет, снятый с pravoe-delo.su (D-006). Дефолтный `font-family` меняется на `"Roboto Condensed", "Arial Narrow", Arial, sans-serif` (без подключения Google Fonts внутри Shadow DOM — сайты, уже загрузившие Roboto Condensed в `<head>`, получают точный шрифт бесплатно за счёт того, что `@font-face` не скоуплен границей Shadow DOM; остальные сайты мягко деградируют до `Arial Narrow`/`Arial`). Добавлены hover/active-состояния через `filter: brightness()` для плавающей кнопки и кнопки отправки — работает для любого настроенного `--cw-primary`, не только оранжевого. Все значения переносятся в `widget/src/widget.css` как новые дефолты, конфигурируемость через `data-primary-color`/`data-position` (D-004/D-005) не отменяется.
Почему: принято по результатам приёмки TASK-004 (`team/design/design-system.md`) — дизайнер прямо зафиксировал смену дефолта с обоснованием (замечание №1 отчёта), тим лид согласен: раз у проекта уже есть конкретный целевой сайт (D-006), логичнее дефолтить на его бренд, чем на произвольный синий, при этом ничего не запрещает переопределить цвет конфигом на других сайтах.
