# Протокол работы команды

Единые правила для всех ролей. Каждый скил обязан следовать этому протоколу.

## Структура папки team/

```
team/
  PROJECT.md      — описание проекта: цель, стек, ограничения (заполняет тим лид при инициализации)
  BACKLOG.md      — список всех задач со статусами (ведёт тим лид)
  DECISIONS.md    — журнал архитектурных решений (ведёт тим лид)
  PROTOCOL.md     — этот файл
  tasks/          — задания: TASK-001.md, TASK-002.md ...
  reports/        — отчёты исполнителей: TASK-001-report.md ...
  templates/      — шаблоны задания и отчёта
```

## Статусы задач

| Статус | Значение |
|---|---|
| `TODO` | Задача создана, не взята в работу |
| `IN_PROGRESS` | Исполнитель работает |
| `REVIEW` | Работа сдана, ждёт приёмки тим лидом |
| `REWORK` | Тим лид вернул с замечаниями |
| `DONE` | Принято и смержено в main |
| `BLOCKED` | Заблокирована другой задачей |

Статус хранится в двух местах и должен совпадать: в шапке файла задачи и в строке задачи в `BACKLOG.md`. Кто меняет статус — обновляет оба места.

## Git

- Репозиторий обязателен. Если его нет — тим лид делает `git init` при инициализации проекта.
- Одна задача = одна ветка `task/TASK-XXX`, создаётся от актуального `main`.
- Исполнитель коммитит только в свою ветку. Сообщения коммитов: `TASK-XXX: краткое описание` (на английском).
- В `main` мержит **только тим лид** после приёмки (merge, не rebase).
- Если задача возвращена на доработку (REWORK) — исполнитель продолжает в той же ветке.

## Жизненный цикл задачи

1. **Тим лид** создаёт `team/tasks/TASK-XXX.md` по шаблону, добавляет строку в `BACKLOG.md` со статусом `TODO`, указывает роль и рекомендованную модель.
2. **Пользователь** открывает новый чат, выбирает рекомендованную модель, вызывает скил роли (например `/backend`) и называет номер задачи.
3. **Исполнитель**: читает задачу, `PROJECT.md`, `DECISIONS.md` → ставит статус `IN_PROGRESS` → создаёт ветку → делает работу → сам проверяет по критериям приёмки → пишет отчёт в `team/reports/TASK-XXX-report.md` → ставит статус `REVIEW` → коммитит всё в ветку.
4. **Пользователь** говорит тим лиду: «прими TASK-XXX».
5. **Тим лид** проводит приёмку (см. ниже) → `DONE` + merge в main, либо `REWORK` + замечания в файл задачи.

## Строгая приёмка (правила для тим лида)

Приёмка не бывает «на глазок». Обязательные шаги:

1. Прочитать задание и критерии приёмки.
2. Прочитать отчёт исполнителя.
3. Посмотреть полный diff ветки: `git diff main...task/TASK-XXX`.
4. Прогнать проверки из раздела «Как проверить» отчёта (тесты, запуск, линтер).
5. Пройтись по каждому критерию приёмки и явно отметить: выполнен / не выполнен.
6. Вердикт:
   - **Принято** → merge в main, статус `DONE`, краткое резюме пользователю.
   - **На доработку** → статус `REWORK`, замечания списком в раздел «Замечания по доработке» файла задачи. Замечания должны быть конкретными: файл, проблема, что исправить.

## Выбор модели (правила для тим лида)

У пользователя небольшая подписка — экономия важна. Принцип: **по умолчанию Sonnet, эскалация только по необходимости**.

- **Sonnet** — дефолт для всего: типовые фичи, CRUD, вёрстка, тесты, багфиксы, рефакторинг по понятному плану, отчёты.
- **Opus / Fable** — только когда Sonnet реально может не справиться: проектирование архитектуры с нуля, запутанный дебаг (гонки, память, «мистические» баги), сложные алгоритмы, security-ревью критичного кода, приёмка крупных задач.
- **Haiku** — механика: переименования, массовые правки по шаблону, генерация boilerplate.

В каждой задаче тим лид пишет рекомендованную модель и **одной фразой почему**. Если сомневаешься между Sonnet и Opus — ставь Sonnet, а в задаче пометь: «если застрянешь — вернуть тим лиду на переоценку модели».

## Правила для исполнителей

- Не выходи за рамки задачи. Заметил проблему вне задачи — не чини, а запиши в отчёт в раздел «Замечания для тим лида».
- Не меняй архитектурные решения из `DECISIONS.md`. Не согласен — напиши в отчёте, решает тим лид.
- Не трогай чужие ветки и чужие задачи.
- Перед сдачей обязательно сам пройдись по критериям приёмки — сдавать непроверенное запрещено.
- Все вопросы, требующие решения человека, — списком в конце отчёта.
