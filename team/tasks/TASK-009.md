## Контекст

Пользователь протестировал текстовый поиск (D-009, TASK-008) на демо-странице и получил плохие результаты. Конкретные примеры из отчёта пользователя:

- Запрос **«Какие риски у банкротства?»** → предложены нерелевантные кандидаты «Чем реструктуризация отличается от банкротства?» и «Что будет с кредитной историей после банкротства?» вместо вопросов из категории «Последствия и риски», прямо отвечающих на вопрос о рисках.
- Запрос **«Риски»** (одно слово) → предложены совершенно нерелевантные кандидаты про сумму долга для внесудебного банкротства (`q-018`, `q-003`) — в базе вообще нет вопроса с словом «риски» в тексте, и без `keywords` fuzzy-поиск подставляет случайные совпадения.
- Запрос **«Какие последствия»** → «Точный вопрос не найден», хотя в базе есть целая категория «Последствия и риски» с 6 вопросами.

Корневые причины (проверено чтением `widget/data/qa-data.js` и `widget/src/widget.js`):
1. Поле `keywords` заполнено только у 5 из 24 вопросов (`q-002`, `q-006`, `q-011`, `q-013`, `q-017`) — у остальных 19 нечёткий поиск опирается только на дословный текст вопроса, поэтому не находит смысловые синонимы («риски», «последствия», «минусы»).
2. В базе нет вопроса, который прямо обобщал бы риски/последствия банкротства — только узкие подвопросы (квартира, имущество, кредитная история, выезд за границу, ограничения). Общий запрос «какие риски» не должен предлагать вопросы из других категорий, но должен предлагать хотя бы часть вопросов категории «Последствия и риски».
3. Конфиг Fuse.js в `getFuse()` (`widget/src/widget.js:229`) — `threshold: 0.4`, `ignoreLocation: true` — слишком нестрогий для коротких запросов при пустых `keywords`, из-за чего короткие слова типа «риски» цепляют случайные вопросы из других категорий.

## Задание

Затронутые файлы: `widget/data/qa-data.js`, `widget/src/widget.js`, `docs/features/FEAT-001-linear-dialog.md` (поле `Related data model` / раздел `Related Systems` уже упоминает `keywords` — сверить и обновить формулировку, если поменяется охват).

1. Добавить поле `keywords` (2–5 синонимов/переформулировок на вопрос, на основе реальной лексики из ответа — не выдумывать новых юридических фактов) всем вопросам, где его ещё нет. Опираться на смысл существующего `answer`, ничего не придумывать сверх содержания.
2. В категорию `posledstviya-riski` добавить один новый вопрос-ответ, обобщающий риски/последствия банкротства (например «Какие риски и последствия у банкротства?»), с ответом, который просто перечисляет и ссылается на уже существующие в базе темы этой категории (жильё, имущество, кредитная история, ограничения) — без новых юридических утверждений, которых нет в остальной базе. Присвоить `id` по существующей схеме (`q-025`), добавить релевантные `keywords` (`риски`, `последствия`, `минусы`, `недостатки`).
3. При необходимости скорректировать конфиг `Fuse` в `getFuse()` (`widget/src/widget.js`) — например веса `keys`, `threshold`, `minMatchCharLength` — чтобы короткие обобщённые запросы не давали случайных совпадений из нерелевантных категорий. Обосновать выбор параметров в отчёте.
4. Обновить `docs/features/FEAT-001-linear-dialog.md`, если охват `keywords` меняется с «часть вопросов» на «все вопросы» (строка в `Related Systems` про `widget/data/qa-data.js`).

Что НЕ входит в задачу: изменение сценария кнопочной навигации (D-008), переход на другую библиотеку поиска, добавление новых категорий, любые изменения `widget.css`.
